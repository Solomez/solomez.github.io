A design system for a public-sector HR platform: a month on a ready-made library, then our own

Public-sector HR platform · 604 variables and 116 component sets; developers built all the platform's screens with it

  • One of two designers
  • Studio
  • 2025-2026
Context
a design system for a public-sector HR platform for civil servants, designed for 1 to 2 million users, part of a full redesign of every page: the old interface was hard to use and had no mobile version
Role
one of two designers on the system, at a design studio
Team
two designers, the studio's art director, about 20 developers (my estimate)
When
2025-2026
Status
released on 3 November 2026, users start on 9 November
Numbers from
Figma files, October and November 2026

Client under NDA. I recreated the visuals with placeholder data

In short

A contractor's development team proposed a ready-made component library, and we designed on it for about a month. The screens came out very different from our concept. I audited 24 of its components and showed the same screen made two ways, with the library and as we designed it. After that, the client's leadership decided that we would build our own system

My part is the library audit, the header with navigation, and about half of the components, including buttons, inputs and badges. Two of us built the system, and the second designer leads it now

On the same platform I also worked out AI features for its users, such as smart search: which features to take, how to build them, in what form and with what rules. They are in the November release

The system has 604 variables, and developers have built all the platform's screens with it. On the product's Workplace tab, 1,071 of the 1,171 components on the screens match the system by name (my count in Figma, October 2026)

01 · The library did not have the tokens our screens needed

The audit page has 50 different notes, and they repeated from component to component: no tokens for spacing, stroke width, the hover background, typography, or icon color and size. Some components we could use only after detaching them from the library, which cuts them off from its updates

The library file shows the same: 2,462 variables, but no breakpoints, no z-index values and no text styles, and its button had just two corner radius values for all its sizes and types

02 · I showed the same screen made two ways

I also made a table of the library button's properties and marked each one: its own token for each size, one token shared by all sizes, or no token at all

We showed both versions and the problems from my audit to the client's leadership, and they decided that we would build our own system

03 · Two levels of tokens, by design

The second designer and I came up with the token scheme together. The first level is a palette of 153 colors. The second is 208 role tokens, each with a light and a dark value; most of them take their color from the palette. Typography and the grid switch between three screen widths: from 1280, from 768 to 1279, and up to 767. The system also has 30 text styles

We have no component-level tokens: a component takes a role token directly. We chose this to build the system faster and to be able to extend it to other products later. So far two levels have been enough. The cost: we can't tune one component on its own, so after a change to a role token we have to check each component that uses it

04 · The header fits many links at three screen widths

The header and navigation are mine: 7 component sets. To fit many links, the dropdown menu has one to four columns

05 · One button set where the library had three

Our button is one component set with 234 variants. The library had three sets, one per size, with 655 variants each. The button page also has usage rules. The second designer and I wrote guides like this for 10 components using Claude, and each has a section for developers with tokens for every state and ARIA notes

06 · A component is done after two reviews

The studio's art director reviews a component first. Then we go through it with the developers on several calls. After that it either goes back for changes or counts as done. The developers use the same token names as in Figma and keep their own component library in code, built to match the system. Besides the two of us, other designers at the studio build screens with the system

07 · Developers already build the product from the system

The product files hold two versions of the platform: about 2,000 screens in the first and about 800 in the current one, for desktop, tablet and phone

On the Workplace tab, most of the components that match the system are table cells. Most of the rest come from other shared files, such as the icon kit, and only 6 were made inside the product file (my count, October 2026). On the feed screens, the post, the comment thread and the post editor are not in the system yet: they are still in development

On product screens built from the system, I no longer stop to find out which color, type token or corner radius to use

08 · Research and product work on the same platform

  • I ran a test of the clickable prototype with 8 civil servants on 9 tasks and ranked the findings by severity and frequency. The most common one, unclear section names, came up with all 8. After the test we listed the users' needs and changed the approach to the next concept: for example, users can now hide the banners on the home page

  • I designed sign-in, account recovery and registration for web and phone, 37 states each, and 9 error pages

  • I reviewed the studio's build of the news feed against the layouts and left about 50 notes, from element sizes to a tap that opened a new tab instead of the post

09 · How I used AI

With the studio's approval, I use Claude connected to our team's Figma account. For each component it builds the base structure and names the properties, and I set up the rest myself. A task that would take me 4 to 6 hours takes about 2 this way

Now it also lays out whole screens from the client's requirements with the rules of our design system, and I check each one against the requirements and the system

10 · A borrowed palette: some badges almost vanish into the card

We took the color palette from another system, and in some places elements blend with the background. One example is the "working day" badge in the calendar card: its text has a contrast of 6.5 against the badge fill, but the fill against the card background is only 1.05:1 (my count from the file values). The semi-transparent colors also did not work out as I wanted: this badge fill is green at 8% opacity, so on a light card it almost disappears

Next time I would work out the color palette in more depth and not take a ready-made one
