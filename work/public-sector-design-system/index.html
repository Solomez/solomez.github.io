A design system for a public-sector HR platform: a month on a ready-made library, then our own

  • One of two designers
  • Studio
  • 2025–2026
Context
a design system for a public-sector HR platform for civil servants, part of a full redesign of the platform
Role
one of two designers on the system, at a design studio
Team
two designers, the studio’s art director, about 20 developers (my estimate)
When
2025–2026
Status
in development, release in November 2026
Counts
Figma files, October 2026

Client under NDA. I recreated the visuals with placeholder data.

In short

The whole platform is being redesigned, every page: the old interface was hard to use and had no mobile version. The design system is part of that redesign. A contractor’s development team proposed a ready-made component library, and we designed on it for about a month. The screens came out very different from our concept. I audited the library and showed the same screen made two ways, with the library and as we designed it. After that, the client’s leadership decided that we would build our own system.

My part is the library audit, the header with navigation, and most of the basic components, such as buttons and badges. Two of us built the system, and the second designer leads it now. By my estimate, more than half of the 116 component sets are mine.

The system has 604 variables and 116 component sets, and developers already build screens with it.

01 · The library did not have the tokens our screens needed

I went through 24 components of the library and wrote down what each one lacked. The notes repeated from component to component: spacing was not in tokens, there was no token for stroke width or for the hover background, typography was not in tokens, and icon color and size had no tokens either. Some components we could use only after detaching them from the library, which cuts them off from its updates.

The library file shows the same: 2,462 variables, but no breakpoints, no z-index values and no text styles.

For the product screens, three things were missing: settings for a table cell with a second line and an avatar, a vacation card component, and tokens and settings for our version of the header.

02 · I showed the same screen made two ways

I put the same modal window side by side: once built with the library and once as in our concept. I also made a table of the library button’s properties and marked each one: its own token for each size, one token shared by all sizes, or no token at all.

Then the question went to the client’s leadership, and they decided that we would build our own system.

03 · Two levels of tokens, by design

The second designer and I came up with the token scheme together. The first level is a palette of 153 colors. The second is 208 role tokens, such as text or background colors, each with a light and a dark value; most of them take their color from the palette. Typography and the grid switch between three screen widths: from 1280, from 768 to 1279, and up to 767. Base numbers such as spacing, sizes, radii, durations, z-index values and breakpoints have their own variables. The system also has 30 text styles.

We have no component-level tokens: a component takes a role token directly. We chose this to build the system faster and to be able to extend it to other products later. So far two levels have been enough, and I think this is also why new components are quick to build. The cost: without a component level, we can’t tune one component on its own, so after a change to a role token we have to check each component that uses it.

04 · The header fits many links at three screen widths

The header and navigation are mine: 7 component sets and 26 variants. To fit many links, the header has versions for three screen widths, a dropdown menu with one to four columns, and a bottom sheet on a phone.

We looked at how other services solve this and agreed on one version as a team.

05 · One button set where the library had three

I built most of the basic components, and the button is one of them. Ours is one component set with 234 variants. The library had three sets, one per size, with 655 variants each. The button page also has usage rules: when to use it, anatomy, hierarchy, tone and placement. I wrote them together with the second designer.

06 · A component is done after two reviews

Each component has its own page in the Figma file, and the page name shows its status: planned, in progress, needs review, or deprecated. The list has no “done” status yet, so finished components still say “needs review”. The studio’s art director reviews a component first. Then we go through it with the developers on several calls. After that it either goes back for changes or counts as done. The developers use the same token names as in Figma.

The developers get the variables as a file exported from Figma, and they keep their own component library in code, built to match the system. When a component changes, we publish the library update in Figma and write in the team chat what changed. Besides the two of us, other designers at the studio build screens with the system.

07 · How I used AI

With the studio’s approval, I use Claude connected to our team’s Figma account to draft components. For each component it builds the base structure and names the properties; I set up the rest myself. A task that would take me 4 to 6 hours takes about 2 this way. Most often I remove states it added that we do not need, and sometimes I change what is inside the component. I check all of this work several times. I also used Claude to compare how other design systems solve the same components.

08 · Developers already build the product from the system

The product is in active development, and the developers have already built screens with the system. The product file has 919 screens.

On the product’s Workplace tab, with its work calendar and tables, almost every component on the screens comes from our system: 1,071 of 1,171, most of them table cells. Most of the rest come from other shared files, such as the icon kit, and only 6 were made inside the product file (my count by component name, October 2026). On the feed screens, the post, the comment thread and the post editor are not in the system yet: they are made inside the product file and are still in development.

My work now is mostly product screens built from the system, and I add the states that are still missing. On these screens I no longer stop to find out which color, type token or corner radius to use.

09 · A borrowed palette: some badges almost vanish into the card

We took the color palette from another system, and in some places elements blend with the background. One example is the “working day” badge in the calendar card: its text has a contrast of 6.5 against the badge fill, but the fill against the card background is only 1.05:1, almost no difference, since 1:1 means the same color (my count from the file values). The semi-transparent colors also did not work out as I wanted: this badge fill is green at 8% opacity, so on a light card it almost disappears.

Next time I would work out the color palette in more depth and not take a ready-made one.
